# Development status — 2026-08-30

## Work completed

### Phase 1 — foundation
- Aqara OAuth2 account discovery remains the authentication model; user passwords are not collected by Homey.
- Multiple camera pairing remains enabled; `list_devices` does not use `singular: true` and each camera is keyed by Aqara DID.
- Aqara API signing was isolated into `lib/aqara/signature.js` and aligned with Aqara's documented header ordering and lowercase MD5-32 algorithm.
- Aqara API region domains were centralized in `lib/aqara/regions.js` for EU/US/CN/KR/RU/SG. The current OAuth client still uses EU; selectable-region OAuth is deliberately not enabled until the complete OAuth flow is tested for each region.
- Camera model IDs were moved to `lib/aqara/camera-models.js` so discovery and future feature support can evolve independently.
- Transient network failures now use exponential backoff with bounded retries.
- Permanent Aqara business error codes are not incorrectly treated as HTTP 5xx errors.
- Added secret redaction helpers for RTSP credentials, tokens, keys and passwords.
- Aqara device pagination now has duplicate protection and a safety limit.
- Flow action listeners are registered once at driver level instead of once per camera device. This is an important multi-camera stability fix.
- Device lifecycle cleanup now handles RTSP registrations and health timers.
- Camera health is checked conservatively every 10 minutes rather than through aggressive polling.
- Privacy-mode mapping was normalized: `onoff=true` means camera active/privacy off; privacy action `true` means privacy mode enabled.
- Added device-level event hooks for motion/person/sound so a future Aqara event bridge can trigger Homey Flow cards without changing the device API.

### Phase 2 — camera integration foundation
- Native Homey RTSP video remains per-camera.
- Aqara snapshot implementation remains available.
- Custom camera-view stream hook remains available.
- Privacy, light/IR and microphone controls remain isolated as camera operations.
- Unsupported model features are no longer implied by a giant hardcoded feature list; model metadata is centralized.

### Phase 3 — recording foundation
- Added `recorder/` companion-service documentation.
- Added MediaMTX Docker Compose service.
- Added multi-camera MediaMTX configuration example with independent paths.
- Recording is designed to happen on NAS/Proxmox/Docker, not inside Homey's application process.
- MediaMTX is configured as the future point for fragmented-MP4 recording, retention and playback.

### Phase 4/5 — storage foundation
- NAS is the recommended primary target.
- Google Drive is explicitly a secondary/off-site target.
- Added Google Drive backup design using rclone on the recorder host.
- Documented per-camera folder structure and example retention policies.

### CI / quality
- Added Node unit tests for Aqara signature generation and camera model discovery.
- Added tests for credential redaction.
- Added GitHub Actions test workflow.
- Existing Homey asset/build workflow remains responsible for generated assets and publish-level validation.
- Added roadmap and this status report so the project state remains visible in GitHub.

## Non-negotiable architecture

- Unlimited practical multi-camera design: every camera is keyed by Aqara DID.
- One camera failing must not stop other cameras.
- Homey is the controller/orchestrator, not the 24/7 NVR.
- RTSP is per camera.
- Recording is per camera.
- Storage policy is per camera.
- Aqara OAuth and Google Drive OAuth remain separate security domains.
- No credentials are committed to Git.
- Unsupported Aqara resources must fail clearly rather than being simulated.
